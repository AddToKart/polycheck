## Critical

### C1. Teacher "Enroll Student" always fails with HTTP 400 `[verified-source]`

- **Files:** `frontend/src/lib/api-client.ts:422-424`, `backend/src/sections/dto/enroll-student.dto.ts:3-11`, `backend/src/main.ts:47-53`
- **What happens:** the client posts the whole `EnrollStudentInput` (`sectionId`, `studentId`, `studentName`) to `POST /sections/:id/enroll-student`, but the DTO only allows `studentId` and `studentName`; the global `ValidationPipe` runs with `forbidNonWhitelisted: true`, so every call returns `400 property sectionId should not exist`.
- **Why it matters:** the handler `handleEnrollStudent` (`frontend/src/app/faculty/sections/[id]/page.tsx:116-125`) has no `catch`, so the roster never updates and no error is shown.
- **Trigger:** section detail → Enroll Student → pick any student.
- **Evidence:**
  ```ts
  // frontend/src/lib/api-client.ts:422-424
  enrollStudent(data: EnrollStudentInput): Promise<boolean> {
    return post(`/sections/${data.sectionId}/enroll-student`, data)
  }
  ```
  ```ts
  // backend/src/sections/dto/enroll-student.dto.ts
  export class EnrollStudentDto {
    @IsString() @MinLength(1) studentId!: string
    @IsString() @MinLength(1) studentName!: string
  }
  ```
- **Fix direction (not applied):** destructure out `sectionId` before posting (web + mobile both post the full object), or add an optional `sectionId` to the DTO and validate it against the path. Add a contract test that pipes `EnrollStudentInput` through the real validation pipe.

### H1. Teacher manual-enroll has no error handling on the section page `[verified-source]`

- **File:** `frontend/src/app/faculty/sections/[id]/page.tsx:116-125`

### H2. Resolved-disputes view is empty after reload `[verified-source]`

- **Files:** `frontend/src/app/faculty/disputes/page.tsx:106`, `backend/src/disputes/disputes.service.ts:33,44-47`
- **What happens:** the page calls `api.getDisputedRecords()` with no `status` filter; the backend defaults to `status = 'pending'` (`where.status = 'disputed'` + `disputeResolved = false`). Records resolved in-session appear only because `handleResolve` (page lines 116-124) mutates local state; any refresh loses them. `resolvedCount` (line 171) is always 0 on load.
- **Trigger:** resolve any dispute → reload the page → open "Resolved" tab → empty.

### H3. Student dispute submission fails with no feedback `[verified-source]`

- **File:** `frontend/src/app/student/dashboard/page.tsx:146-158`
- **What happens:** there is no `try/catch`; `api.submitDispute` throws on non-2xx, so the `else` branch at line 152 (`Failed to submit dispute.`) is unreachable. The modal stays open with no message and an unhandled rejection is logged.
  ```ts
  const result = await api.submitDispute({ recordId: disputeRecord.id, reason: ..., description: disputeDescription })
  if (result) { setDisputeFeedback({ type: 'success', ... }) }
  else { setDisputeFeedback({ type: 'error', ... }) } // unreachable on failure
  ```
- **Trigger:** submit with a description that the backend rejects (validation), while offline, or after a 401.

### H4. Faculty schedule Week view drops classes across a month boundary `[verified-source]`

- **File:** `frontend/src/app/faculty/schedule/page.tsx:481-494, 498-508, 622-634`
- **What happens:** `events` are always generated from `getDateRangeForMonth(currentYear, currentMonth)`, and week navigation (`goToPrev`/`goToNext`, lines 512-532) only mutates `currentDate`. `WeekView` (line 633) receives the `currentDate` week but events/attendance scoped to `currentMonth`, so a week that spills into the next/previous month renders empty.
- **Trigger:** `/faculty/schedule` → Week → Next until the week crosses into the next month → grid is empty despite scheduled classes.

### H5. Faculty dashboard hangs forever when the initial load fails `[verified-source]`

- **File:** `frontend/src/app/faculty/page.tsx:51-68`
- **What happens:** `fetchData` has no `try/catch`; `setLoading(false)` (line 65) only runs after `Promise.all` resolves. A single network/5xx failure leaves the page on the spinner and leaks an unhandled rejection.
- **Same pattern reported:** `faculty/sections/[id]/page.tsx:60-87`, `faculty/subjects/page.tsx:19-36`, `student/schedule/page.tsx:418-440` `[audit-reported]`.
- **Trigger:** load `/faculty` with the API down.

### H6. Mobile faculty session cockpit is blank offline `[verified-source]`

- **Files:** `android/app/(faculty)/sessions/[id].tsx:54-67, 69-80, 116`, `android/services/api-client.ts:528, 720`
- **What happens:** `refreshData()` awaits `Promise.all([getSession, getAttendanceRecords, getProofsOfClass])`. `getAttendanceRecords` and `getProofsOfClass` are plain `get()` calls with no cache fallback, so offline the promise rejects, `setSession(nextSession)` never runs, and the mount effect never sets `session` itself. Line 116 (`if (!user || !session) return null`) renders a blank screen. Even after `generateQr()` succeeds via the offline path (api-client.ts:492-504) the QR is never displayed.
- **Trigger:** pre-sync online → go offline → open a session → blank; tap Generate (queues activation) → still blank.

### H7. Redundant signing-key provisioning exhausts the 3/hour server limit `[verified-source]`

- **Files:** `android/services/api-client.ts:81, 273-277, 483-486`, `backend/src/auth/auth.service.ts:27-28, 155-164`, `android/components/CampusLoginPortal.tsx:34-47`
- **What happens:** `provisionedTeacherKeys` is an in-memory `Set`; `loginFaculty` always re-posts `/auth/provision-key` after every login, and `generateQrCode` re-posts after every app restart. The server allows 3 provisions per 3600 s, so the 4th login or first QR after the 4th launch throws 429.
- **Extra impact:** during faculty login, the session is already established and `notifyAuthListeners()` has fired before the provision call; the 429 makes `CampusLoginPortal` show "Unable to sign in" and skip the post-login redirect, leaving a signed-in user stranded on the login screen.
- **Trigger:** sign in as faculty (or generate a QR) on 4 fresh app launches within an hour.

## Medium — Backend

### M1. Department-scoped super admin can read other departments' sections and enrollment codes `[verified-source]`

- **File:** `backend/src/subjects/subjects.service.ts:20-48`
- **What happens:** `findOne` scopes the subject with `adminSubjectWhere`, but the nested `sections` include has no admin filter (only teacher/student branches; `undefined` for super admins). Every section of a cross-department subject — including `enrollmentCode` and `enrollmentCodeExpiry` (join secrets) — is returned.
- **Contrast:** `SectionsService.findOne` correctly applies `adminCanAccessSection` (`sections.service.ts:76-78`); this endpoint is the outlier.
- **Trigger:** department-scoped super admin (`scope='department'`) calls `GET /subjects/:id` for a subject with one in-department and one out-of-department section.

### M2. Disputes can be re-resolved, and non-disputed records can be "resolved" `[verified-source]`

- **File:** `backend/src/disputes/disputes.service.ts:80-109`
- **What happens:** `resolve` never checks `record.status` or `record.disputeResolved`. A second POST overwrites the first decision with no revision history; any record id can be flipped to any status. Expected: only `status='disputed' && disputeResolved=false` may be resolved.
- **Trigger:** call `POST /disputes/:id/resolve` twice, or on an attendance record that was never disputed.

### M3. `PATCH /sections/:id` schedule validation holes `[verified-source]`

- **Files:** `backend/src/sections/dto/update-section.dto.ts:4-20`, `backend/src/sections/sections.service.ts:130-144`
- **What happens:** the update DTO marks `day`, `startTime`, `endTime` as bare `@IsString() @IsOptional()` (create DTO has `@IsIn` + `@Matches`), and the service casts `s.day as DayOfWeek` / non-null-asserts times.
  - Missing `day` → Prisma error → HTTP 500.
  - `{ day: 'Mon', startTime: '25:00', endTime: '26:00' }` passes `assertScheduleRanges` (string compare) and the DB check constraint, persisting corrupt rows.
- **Also missing:** `@ArrayMaxSize` present on create.
- **Trigger:** the two PATCH bodies above.

### M4. Unique-constraint violations surface as 500 instead of 409 `[verified-source for the service gap]`

- **Files:** `backend/src/subjects/subjects.service.ts:51-63`, `backend/src/sections/sections.service.ts` (create/update; only `createEnrollment` at line 394 handles P2002), `backend/src/common/filters/all-exceptions.filter.ts:46-53` `[audit-reported for filter mapping]`
- **What happens:** duplicate subject `code` or duplicate `[subjectId, section, semester, teacherId]` reach Prisma, the P2002 error is rethrown, and the global filter maps unhandled errors to 500.
- **Trigger:** `PATCH /subjects/:id {"code":"<already used>"}` or `POST /sections` with a duplicate composite key.

### M5. Dashboard overview breaks at scale `[verified-source]`

- **File:** `backend/src/dashboard/dashboard.service.ts:140-150`
- **What happens:** all sessions in a user-selectable range (up to 90 days; institution-wide) are loaded only to build an `id → date` map, then every id is inlined into `sessionId: { in: [...] }`. Prisma expands the list to one bind parameter per id; PostgreSQL's protocol limit is 65,535 → 500s and memory pressure on large data.
- **Trigger:** `GET /dashboard/overview` with a 90-day range containing >65k sessions in scope.

### M6. CSV "Student ID" contains the internal `User.id`, not the student number `[verified-source]`

- **File:** `backend/src/dashboard/dashboard.service.ts:193, 205, 221`
- **What happens:** header is `['Student', 'Student ID', ...]` but the value written is `AttendanceRecord.studentId`, which is an FK to `User.id` (`schema.prisma:287-288`; migration `AttendanceRecord_studentId_fkey`). The PUP student number lives on `User.studentId` (`schema.prisma:42`). Exports show `s-001`/cuid instead of `2024-00001-MN-0`.
- **Judgment:** likely a wrong-column bug, not just a rename — confirm intent.

### M7. Proof upload limit is not reachable as configured `[verified-source]`

- **Files:** `backend/src/proofs/proofs.controller.ts:11`, `backend/src/proofs/proofs.service.ts:124`, `backend/src/common/config/env-validation.ts:25`
- **What happens:** `photoData` is capped at 7,000,000 chars ≈ 5.25 MB decoded, while `MAX_PROOF_BYTES` can be configured up to 10 MB. Images between 5.25 MB and the configured max get a 400 before the service sees them.
- **Trigger:** configure `MAX_PROOF_BYTES=10000000`, upload a ~7 MB image.

### M8. WebSocket CORS diverges from HTTP CORS `[verified-source]`

- **Files:** `backend/src/realtime/attendance.gateway.ts:19-32`, `backend/src/main.ts:32-43`
- **What happens:** the gateway allowlist reads raw `process.env.CORS_ORIGINS` only. HTTP CORS applies defaults (`http://localhost:3000,http://localhost:8081`) and appends `FRONTEND_URL`; neither is written back to `process.env`. An origin accepted by REST can be rejected on the `/attendance` handshake, silently degrading realtime to polling.
- **Trigger:** backend started with `FRONTEND_URL` set but `CORS_ORIGINS` missing that origin.

### M9. "Web" accuracy relaxations are selected by client-controlled fields `[verified-source]`

- **File:** `backend/src/attendance/scan-validator.service.ts:188-206`
- **What happens:** `isWeb = deviceId.startsWith('web-') || inputChannel === 'image'` raises the max accepted accuracy from 50 m to 500 m and skips the `geofence_uncertain` rejection entirely. Any client can send `inputChannel: 'image'` (a DTO-permitted value) regardless of platform.
- **Impact:** weakens defense-in-depth rather than enabling a new bypass (coordinates/accuracy are self-reported), but the policy signal should be server-derived.

### M10. Signing-key rotation can race session activation `[audit-reported]`

- **Files:** `backend/src/sessions/sessions.service.ts:174-209`, `backend/src/attendance/attendance.service.ts:451-514`, `backend/src/auth/auth.service.ts:166-184`
- **Claim:** rotation holds `key-rotation:<teacherId>` across the key write, but activation reads the public key and verifies the token without the lock (the lock is taken only later for cache publication). If rotation commits between the key read and the atomic activation claim, the session stores a token signed by a rotated-out key and cannot be re-activated. **_Un-reproduced; timing-dependent, millisecond window._**

### M11. Enrollment-code TOCTOU `[audit-reported]`

- **Files:** `backend/src/sections/sections.service.ts:227-245` vs `:377-399`
- **Claim:** `enrollViaCode`/`enrollByCode` validate the code and expiry outside `createEnrollment`, whose advisory-locked transaction re-checks only duplicate enrollment — not the code/expiry. A concurrent reset/disable cannot stop an in-flight enrollment.

## Medium — Shared package

### M28. `getMonthDays` emits an all-null trailing week; `getWeeksInMonth` overcounts `[verified-source]`

- **File:** `shared/src/utils/calendar.ts:113-118`
- **What happens:** after padding, `if (week.length > 0)` is always true, so when a month ends exactly on Saturday the empty week is pushed.
  ```ts
  while (week.length < 7) { week.push(null) }
  if (week.length > 0) { weeks.push(week) }  // always true
  ```
- **Examples:** `getMonthDays(2026, 0)` (Jan 2026 starts Thu, ends Sat) → 6 rows, last all-null (expected 5); `getMonthDays(2026, 1)` (Feb 2026 starts Sun, 28 days) → 5 rows (expected 4). Affects web faculty/student schedules and mobile faculty schedule.

### M29. Exported validation schemas contradict their own API types `[verified-source]`

- **File:** `shared/src/validation/index.ts:29-49, 71-81`
- **Issues:**
  - `SectionCreateSchema` requires `teacherId`/`teacherName`, but `CreateSectionInput` (`types/api.ts:31-37`) and `CreateSectionDto` have neither (teacher is derived from auth in `sections.service.ts:106`). Any consumer parsing a `CreateSectionInput` throws.
  - `AttendanceRecordSchema` requires `timestamp` + `coordinates` and omits `status`, so it validates neither the `AttendanceRecord` type nor the manual-add payload sent by clients (`frontend/src/lib/api-client.ts:320-322`, `android/services/api-client.ts:551-553`).
  - `GeofenceConfigSchema.radiusMeters` is `z.number()` while the backend enforces `@IsInt()` — non-integers pass the schema and 400 at the API.
- **Note:** currently referenced only inside `validation/index.ts` (no production consumer), so impact is latent.

### M30. `isTokenInValidityWindow` has no lower bound `[verified-source]`

- **File:** `shared/src/utils/token.ts:85-97`
- **What happens:** `if (now <= validityEnd) return valid` accepts a token whose `issuedAt` is in the future for its entire validity+grace from that future instant. Backend/mobile callers add their own skew guards; the function is currently test-only.

### M31. Two "today" helpers with different timezones are mixed `[verified-source; runtime-dependent]`

- **File:** `shared/src/utils/calendar.ts:26-28` (`formatDate`, local getters) vs `:35-37` (`formatCampusDate`, fixed UTC+8)
- **What happens:** on devices/CI outside UTC+8 the "today" highlight and week range can be off by one day. Mobile rebinds the helper by hand (`android/app/(tabs)/schedule.tsx:22`) as compensation.

### M32. `getStudentSections(studentId)` sends a param the backend ignores `[verified-source]`

- **Files:** `shared/src/types/api.ts:252`, `frontend/src/lib/api-client.ts:232-234`, `android/services/api-client.ts:398-402`, `backend/src/sections/sections.controller.ts:14-17`
- **What happens:** clients call `/sections?studentId=...`; the controller only reads `subjectId`. Accidentally correct for the current authenticated-student callers; silently wrong for any staff caller.

### M33. `getSectionStudents` type promises fields the backend does not return `[audit-reported, code-consistent]`

- **Files:** `shared/src/types/api.ts:249-253`, `backend/src/sections/sections.service.ts:184-200`
- **Claim:** interface says `Student & { attendance }`; the backend selects only `id, studentId, fullName, email, program, yearLevel, photoUrl` — missing required `Student` fields (`role`, `isActive`, `enrolledSectionIds`, timestamps). Latent type hole for future consumers.

### M34. `tsup` `clean: true` can race subpath emits `[audit-reported]`

- **File:** `shared/tsup.config.ts`
- **Claim:** the root config cleans `dist/` while the `utils`/`map` configs emit in parallel (tsup 8 runs config arrays via `Promise.all`); currently benign since no shared chunks exist, but a latent delete race.

- **L1. `check` and `submit` share one rate-limit bucket** — `attendance.service.ts:130` (30/60) vs `:177` (10/60), same key `scan:${user}:${session}`; the 30/min limit is unreachable in a mixed flow. `check` has no production callers today. `[verified-source]`

## Ruled out / checked clean

These areas were traced end-to-end (controller → service → Prisma, or component → client → API) and no defect was found. Recorded so nobody repeats the work:

- **QR token verification:** signature verification, payload encoding/tamper rejection, binding to session/section/teacher, string-equality against the stored token, DB-authoritative public-key read on every scan.
- **Expiry/grace math:** shared utility and backend use identical strict boundaries; activate, offline activation, scan validation, and the auto-expiry cron agree.
- **Replay/duplicate protection:** `(session, student)` unique constraint, `clientAttemptId` replay detection, `tokenSnapshot`/`acceptedScanAttemptId`/`manuallySet` scan guards.
- **Geofence:** Haversine formula, radians conversion, Earth radius, meter units, lat/lng order at every call site; server re-validates on every path including delayed sync.
- **Session lifecycle:** atomic `updateMany` claims prevent double activation/reactivation; end/auto-end are claim-guarded; cache is advisory with DB fallback on every validation.
- **Authorization sweep:** no IDOR found in attendance, sessions, subjects, sections, proofs, disputes, enrollments, section roles, or session permissions; super-admin mutating classroom routes are role-guarded (policy test exists); removal side effects (roles/permissions) are transactional.
- **Web auth/session handling:** `restoreSession` only clears on authoritative 401/403; no redirect loops; no open redirect on login; HttpOnly cookies; nonce-based CSP.
- **CSV export escaping:** all fields quoted; formula injection neutralized; cursor-based pagination bounded.
- **Dashboard scoping** for teacher/student/department admin; campus date arithmetic on PUP-timezone devices.
- **Mobile offline security:** account-scoped encrypted SQLite, owner filtering on every query, queue dedup/idempotency, signing-key account scoping, scanner focus lifecycle and in-flight cancellation.
- **API interface parity:** web and mobile clients both `satisfies ApiClient`; method sets match the shared interface.
- **Test suites:** all green (backend 396, frontend 95, android 131, shared 60) — the findings above are untested gaps, not known failures.

## Open questions

1. **Late offline sync semantics:** a delayed valid token can end a never-activated session and mark the whole roster absent (`attendance.service.ts:448-514`), while the online path rejects the same token. Is this deliberate "offline activation recovery"? Both backend audits flagged it as product-intent dependent.
2. **Account disable and signing keys:** should disabling a teacher implicitly revoke `teacherPublicKey` (L10), or is explicit `POST /auth/revoke-key` the only intended path?
3. **`MAX_PROOF_BYTES`:** is a value above ~5.25 MB a supported deployment configuration (M7)? If yes, the DTO cap must be raised in lockstep.
4. **CSV "Student ID":** was `User.studentId` (the PUP number) intended, or is the internal id acceptable? M6 is a data bug if the former.
5. **`getStudentSections(studentId)`:** is it meant to serve staff callers (M32)? If not, the parameter should be removed; if yes, the controller must read it.
6. **Dispute re-open semantics:** should a resolved dispute be re-openable only via a new `POST /disputes` (which currently allows it), and should `resolve` reject records that were never disputed (M2)?
7. **Web accuracy policy:** should the 500 m / no-uncertainty-check browser policy be derived from a server-side signal (User-Agent/session) instead of client-declared `inputChannel`/`deviceId` (M9)?
8. **Swagger production access:** is the documented token-via-reverse-proxy workflow intended (L12), or should the UI be exempted from the bearer middleware?
9. **`Session.teacherId` FK:** add referential integrity (L6), or is the missing FK deliberate for seed/script flexibility?

## Audit method and limitations

- Six parallel read-only module audits: backend QR/attendance core, backend auth/security, backend CRUD/data, frontend, android, shared. High/Medium findings were then re-verified directly against current source by the coordinating agent; `[verified-source]` marks those.
- No application, database, or device was run for this report; no runtime reproduction was performed. `[runtime-dependent]` items need an environment (HTTP LAN origin, offline device, large dataset) to observe.
- No production systems were touched, no secrets were read, and no source files were modified. This document is the only artifact produced.
